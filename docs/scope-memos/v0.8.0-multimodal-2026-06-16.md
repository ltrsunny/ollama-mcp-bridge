**COMPREHENSIVE ABILITY + CONSOLIDATION (Auditor: "were you choosing for general capability? do
per-task models add hardware overhead?") — yes / yes, and that drives the tier design:**
- *General visual ability (not just OCR):* Qwen3-VL-4B img-**classify** receipt→`receipt` ✓ (flow→
  `screenshot`, borderline vs `diagram`); img-**summarize** the flowchart → *"a decision tree that
  classifies a source_uri into a VLM tier (V for image, B/C for text) based on whether the source is an
  image"* — genuine **visual reasoning**, not a label dump. So it serves `classify`/`summarize` over
  images, not only `extract`.
- *Text parity with tier B (Qwen3-4B-Instruct-2507):* head-to-head on SHORT text (summarize/classify/
  extract) → identical-quality, AND on a **real 1823-word / 4202-prompt-tok doc**: summarize (3
  bullets) + transform (tweet) equal-quality; **extract (tier-table → strict JSON over long text)
  byte-identical AND faster (19.8 s vs 27.0 s)**. Qwen3-VL-4B is a Qwen3 LM backbone + vision — a
  competent TEXT model on long input too (slightly slower on prose, ~24 s vs 21 s summarize).
- *Context window (concern defused):* Qwen3-VL-4B `max_position_embeddings` = **262144 (256 K) — equal
  to tier B**, far above tier C's config; the "VLM has a smaller text context" worry is false.
- *Hardware-overhead finding (concrete):* oMLX is **one-hot** on 16 GB. A captured `400` proved image
  prefill needs **~2.3 GB headroom** (`prefill memory guard: ~12.13 GB peak > 11.84 GB ceiling`) — so a
  session ping-ponging a text tier ↔ a separate image tier pays repeated cold-loads AND can hit the
  guard under accumulated pressure. **Per-task models = real overhead.**
- **→ Decision: ONE small model for BOTH short-text and image.** Qwen3-VL-4B *replaces* the separate
  text tier B (text-parity proven) AND is tier V — the common case keeps a single model hot, no
  text↔image ping-pong, lower memory pressure. Tier C (Qwen3-8B, 32 K long-context) and D (opt-in)
  unchanged. **Validation gate (impl):** parity is now shown on short + a real 1823-word doc + equal
  256 K context; before fully RETIRING B, run a broader regression (multiple docs, `transform`,
  `diff-semantic-index`, near-full-ctx) — until ratified, keep B as a fallback. This is the direct
  answer to "do per-task models add overhead" — the design now *minimizes* model count.

**Robustness checks (Auditor: "run the remaining two"):**
- **Quantization — 4-bit is not lossy here.** 4-bit vs 8-bit Qwen3-VL-4B on the hard suite scored
  **8/12 each, field-for-field identical** — but 8-bit is **4.8 GB vs 2.9 GB (1.65×) and ~2× slower**
  (receipt 8.5 s vs 4.0 s; dense 22.5 s vs 13.4 s). On a one-hot 16 GB Mac, **4-bit wins decisively**
  (zero quality delta, half the footprint, double the speed). The "4-bit degrades vision" worry is
  empirically false for this model/task.
- **Real (non-synthetic) pixels.** A real document (project CHANGELOG) rendered through macOS **Quartz**
  (genuine antialiasing/kerning, not PIL crisp bitmap) → Qwen3-VL-4B transcribed it near-perfectly
  (only trivial markdown-level / em-dash / URL-tail normalizations, no OCR errors) and extracted the
  version list correctly. The synthetic suite's degradation (rotation/noise/blur/JPEG, §0.5) plus this
  real-render check cover the realism gap. *Residual:* not tested on a true camera photo (lens/sensor
  noise) — folded into the §6 post-impl dogfood gate.

Images are the most token-expensive bytes in the frontier (one image ≈ hundreds–thousands of tokens; a
screenshot or multi-page PDF far more). The bridge is text-only → it cannot offload image/screenshot/PDF
work, so those bytes hit the frontier at full cost. A local VLM tier lets the bridge run
`extract`/`classify`/`summarize` over images locally — the **single highest-value mission extension**
(bigger per-call frontier saving than any text case). Mission-aligned EXPANSION, not an original
documented requirement (v0.1.2 envisioned PDF→text, deferred; no vision scenario anywhere).

**Non-goals (this memo):** replacing the text tiers (KEEP Qwen3 B+C, unaffected — additive only);
video (the model supports it, but out of scope v0.8); image *generation* (we only consume images).

## §2 Design forks — for the fanout to challenge (voices rebut EACH OTHER, debate-to-dry)

### FORK 1 — tool surface: extend existing vs new dedicated tools
- **(a) Extend `extract`/`classify`/`summarize` to accept an image `source_uri`** (lead). MIME/extension
  detection on the `source_uri` routes image-bearing calls to the VLM tier automatically; text calls
  unchanged. Reuses existing contracts + the "source_uri preferred" idiom. Minimal new surface.
- (b) New dedicated tools (`describe-image`, `ocr-extract`). Clearer intent, but doubles surface +
  duplicates schema plumbing.
- **PM lean: (a)** — the `source_uri` abstraction already hides file/http; image is one more content
  type behind it. Smallest surface, contracts transfer (proven §0.4).
- *Challenge target:* does auto-routing by MIME hide a footgun (user expects text summarize, passes an
  image by mistake, silently pays VLM latency)? Is an explicit `modality` hint safer than sniffing?

### FORK 2 — VLM pick: Qwen3.5-4B (validated) vs MiniCPM-V-4.6 (untested) — A/B gate
- Qwen3.5-4B: apache, 2.9 GB, same family as text tiers (op simplicity), **already validated §0**,
  image+video. MiniCPM-V-4.6: apache, **2.0 GB** (RAM edge on 16 GB), OpenBMB's efficient CJK VLM,
  NOT downloaded, untested.
- **PM lean: Qwen3.5-4B as baseline; confirm via an IMAGE A/B** on a small suite where they actually
  differ — dense screenshot (UI), a diagram/flowchart, a low-contrast/rotated receipt, a multi-column
  doc — scored on: text fidelity (OCR), CJK, structure correctness, latency, peak RAM. MiniCPM-V wins
  only if it matches quality at materially lower RAM. **A/B is empirical (not fanout) — verify, don't
  vote.**
- *Challenge target:* is one A/B image-suite enough, or is this another "broad query missed candidates"
  trap (e.g. did we miss a stronger small apache VLM — Gemma-3-4B-vision, dots.ocr, GLM-4V — in the PA)?

### FORK 3 — VLM tier & 16 GB memory
- New tier (call it **V**), one-hot like B/C/D (oMLX serializes one model on Metal). Image call → load
  V (evict text); text call → load text. Cold-load ≈ 6–8 s (§0: 11 s incl. first inference).
- *Challenge target:* **thrash** — a session alternating text+image calls pays repeated 6–8 s evictions.
  Mitigations to weigh: (i) accept it (image calls are bursty, not interleaved); (ii) a "sticky VLM"
  hint; (iii) document "batch your image calls". Does the 60 s MCP wall survive cold-load + a big image?
  (§0 cold = 11 s for a small image; a 4 MP screenshot prefill could be far larger — MUST bound.)

### FORK 4 — input handling & security
- `source_uri` → image bytes → base64 data-URI → oMLX. `file://` (local) + `http(s)://`.
- **SSRF:** reuse the sister's `_fetch_url` SSRF + DNS-rebind-pin guard for `http(s)` image fetch
  (don't reinvent). **Size caps:** cap input pixels/bytes; **downscale before send** (a 12 MP phone
  photo → cap longest edge ~1568 px, matching frontier vision norms) to bound prefill tokens + stay
  under the 60 s wall + limit base64 bloat. **MIME allowlist:** png/jpg/jpeg/webp (+ pdf? → FORK 5).
- *Challenge target:* who downscales — the bridge (needs an image lib: Pillow/sips) or trust the model?
  base64 in the request body bloats RAM 1.33× — cap raw input accordingly. Is `file://` path-traversal a
  concern (reuse existing `source_uri` resolver guards)?

### FORK 5 — PDF: in scope, or defer?
- (a) **Defer PDF to v0.8.1** — ship IMAGE-only first (smaller, proven). PDF needs a rasterizer
  (poppler `pdftoppm` / macOS Quartz `sips`) + page-loop + the 60 s wall vs N pages (likely needs the
  async-job path). Real complexity, separable.
- (b) Include PDF now (render-to-image per page → VLM; handles scanned PDFs the deferred text-extract
  couldn't).
- **PM lean: (a) defer** — IMAGE-only is the high-value 80%, fully de-risked; PDF reopens the 60 s-wall /
  multi-page / new-dependency cans best handled with the async-job pattern in its own memo.
- *Challenge target:* is shipping image-without-PDF a coherent product, or will users immediately hit
  "but my receipt is a PDF"? Does deferring PDF strand the feature?

### FORK 6 — enforce-bridge hook & images
- Hook already gates external/large image reads by size (§0 bonus). Add project-internal image
  extensions (`.png/.jpg/.jpeg/.webp`) to the data-file band so in-project images also route to the
  bridge. Keep threat model = self-discipline/token-economy (low false-positive), NOT security.
- *Challenge target:* false-positive risk — devs legitimately Read small UI asset PNGs for non-VLM
  reasons; the 4 KB threshold + edit-marker already handle this, but confirm image-extension gating
  doesn't become the S5-class annoyance the Bash debate warned against.

## §2.5 Debate resolutions — Draft 1 decisions (output of the 2-round fanout)

**blind spots** that all resolve as refinements of the forks above. Decisions:

- **F2 (VLM pick) → CLOSED: tier V = Qwen3-VL-4B-Instruct** (corrected from the Draft-1 Qwen3.5-4B pick

  InternVL3-2B (0/16, non-conforming) ruled out. Molmo / DeepSeek-VL / GLM-4V (fanout leads): HF-checked
  → older/bigger/no-small-permissive-MLX → not pursued; logged so the choice is explicit, not silent.
  - *Qwen3.7 checked (Auditor challenge "no Qwen3.7 attempt?"):* **Qwen3.7 Max / Qwen3.7-Plus exist
    (released 2026-05-18) but are CLOSED/flagship multimodal-agent models — not open-weight, not on HF
    as servable MLX builds, not 16 GB-runnable** → NOT a bridge candidate. The open multimodal line
    stays **Qwen3-VL** (2B/4B/8B/32B; arXiv 2511.21631). Pick unchanged. NB: an HF-only search missed

- **F3 (tier thrash — #1 blocker, 3 concur) → CONSOLIDATE to one small model + sticky + batching.**
  oMLX serializes one model on Metal — parallel tiers are physically impossible on 16 GB. **Primary fix
  (new, from the comprehensive test §0.6): use Qwen3-VL-4B as the SINGLE small model for both short-text
  AND image** — text↔image no longer swaps models, so the dominant thrash source is *eliminated*, not

- **F4 (security — 4 concur) → concrete caps + reuse guards.** (a) `http(s)` images reuse the sister's

  file ≈ 10 MB, **downscale to ≤1568 px longest edge BEFORE base64**, cap the base64 sent to oMLX
  (≈8 MB); malformed image → graceful reject; (d) downscaler = macOS `sips` (zero-dep) preferred,

- **F5 (PDF) → DEFER to a later version (3 concur it's a doc/UX issue, not structural).** v0.8.0 =

- **F6 (hook) → add image extensions to the data-file band; existing guards absorb false-positives.**

- **DEFUSED (do not spend scope on):** stdio-buffer blowup = **misplaced** (3 concur — `source_uri`

- **Process blind spot (noted, not blocking):** R2 wanted real-world workflow/UX testing → added as a

## §3 Token-math (the justification) — grounded

- **Frontier cost of an image (official, `claude-api` skill / Opus 4.7–4.8 migration notes):** a single
  image costs from a few hundred tokens (small) **up to the documented per-image caps: ~1,600 tok on
  ≤ Opus 4.6 (1568 px long edge), ~4,784 tok on Opus 4.8 high-res (2576 px long edge).** Exact counts
  are model-specific via `/v1/messages/count_tokens` (could not run here — no API key; the caps are the
  authoritative anchor). A multi-page PDF / multi-image batch multiplies this.
- **Bridge path frontier cost:** the image bytes **never enter frontier** (the whole point). Only the
  result returns — **~50–170 completion-tok of structured JSON (measured in the A/B)** + tool-call
  overhead ≈ **~150–450 frontier tok total**, regardless of image size.
- **Net saving ≈ image_cost − ~300 ≈ ~1,300–4,500 frontier tok PER IMAGE** — the largest per-call
  saving of any bridge tool. **It compounds in multi-turn:** an image left in frontier context is
  re-billed as input on every subsequent turn until it falls out of the window; the bridge replaces it
  with a one-time ~150-tok JSON. Local cost is ~0 frontier (oMLX: 192 prompt-tok plain / 449 with
  schema, all local).
- **Honest scope caveat:** the saving is real for the bridge's contract — *structured*
  extract/classify/summarize. If the agent genuinely needs full visual fidelity in its own context
  ("look at this UI and reason about the layout visually"), the bridge's structured digest can't
  substitute and the image still belongs in frontier. The feature targets the former, not the latter.
- **Cost paid:** VLM cold-load (~6–8 s, amortized over a burst) + per-image latency (~3–14 s hot per
  §0.5). Must stay < 60 s MCP wall → bounded by the §4 downscale cap (held in the §0.5 large-image test).

- **exists, reuse:** `backendForTool` tier routing (add tier V); `MlxHttpBackend.chat` (already speaks
